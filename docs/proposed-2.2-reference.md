# UI/ — built by design & utility

**The proposed 2.2 interface for every component.** *v2 — validation, events and the three axes folded in.*

Each entry is the component's *real current* props with the 2.2 rules applied, so nothing here is invented and nothing is missing. Generated by `scripts/generate-proposed-reference.ts`, which is also the executable spec for the codemod.

**70 components** on the main surface · **24** in `@pathscale/ui/lab`

## The three axes

| Axis | Answers | Values | |
| --- | --- | --- | --- |
| `variant` | what shape | `solid` `soft` `outline` `ghost` `plain` | closed |
| `flavor` | what it *is* | `neutral` `primary` `secondary` `accent` `destructive` `success` `warning` `info` … | **open** |
| `state` | what is happening *now* | `default` `loading` `disabled` `invalid` `hidden` | closed |

```tsx
<Button>                                       // solid, primary — the call to action
<Button variant="ghost" size="icon">           // chrome
<Button flavor="destructive" state="loading">  // both, no conflict
<Button flavor="hip">                          // theme-defined, no library change
```

## Validation

Every component a user can type into, pick from or toggle extends `Validatable<T>`. **19 components** carry it.

### A result, not a message

```ts
interface Issue {
  code: string;                      // "too_small" — stable and translatable
  params?: Record<string, unknown>;  // { minimum: 8 }
  message?: JSX.Element;             // optional override; skips the i18n lookup
  severity?: "error" | "warning";    // not every issue blocks submission
  path?: (string | number)[];
}
```

`"password too short"` is `{ code: "too_small", params: { minimum: 8 } }`, and the sentence is produced from i18n context. A message baked in English inside the library — which is what `passwordRules.ts` does today — means every non-English app either shows English or rebuilds the result.

### The hard part: showing it *before* the server

Two things are being asked for at once, and conflating them is why inline validation usually feels bad:

| | `Constraint` | `Issue` |
| --- | --- | --- |
| Says | "at least 8 characters" | "too short" |
| Tone | neutral, then satisfied | negative |
| Shown | **live, from the first keystroke** | only once earned |
| Source | the rules, known up front | a failed check |

They are the *same rule at different moments*. Ticking a requirement off as the user types is help. The same rule flashed as "too short" mid-word is nagging. So they are separate props with separate timing.

### Timing

```ts
type ValidateOn = "change" | "blur" | "touched" | "submit";   // default: "touched"
```

`touched` is the only default that is not hostile: **say nothing while they are first typing, surface issues when they leave the field, then revalidate on every keystroke so they can watch themselves fix it.** Reward early, punish late.

| | Behaviour | |
| --- | --- | --- |
| `change` | every keystroke from the start | nags; rarely right |
| `blur` | only on leaving the field | misses the correction feedback |
| `touched` | blur, then live once it has errored once | **the default** |
| `submit` | only on form submit | server-round-trip feel |

### Client and server land in the same place

`issues` is controlled, so a server response sets it directly and it merges with whatever `validate` produced:

```tsx
const [serverIssues, setServerIssues] = createSignal<Issue[]>([]);

<Input
  name="email"
  validate={(v) => v.includes("@") ? [] : [{ code: "invalid_email" }]}
  issues={serverIssues()}          // "that address is already registered"
/>
```

There is no separate error banner and no second rendering path: a server issue looks exactly like a client one, in the same slot, translated the same way.

### Passwords, end to end

The case that motivates the split. Requirements tick live and positive; the failure only appears once earned:

```tsx
<PasswordField
  value={password()}
  onChange={setPassword}
  constraints={evaluatePasswordRules(password(), { minLength: 8, requireNumber: true })}
  showConstraints="unsatisfied"   // fade each one out as it is met
  validateOn="touched"
  issues={serverIssues()}         // "this password has appeared in a breach"
/>
```

`evaluatePasswordRules` already returns `{ key, message, passed }` — it becomes `Constraint[]` by renaming `key` to `code`, `passed` to `satisfied`, and dropping the hardcoded English so i18n supplies the sentence.

`showConstraints`: `always` · `focus` · `unsatisfied` (default for passwords) · `never`.

### It is one label

Both render into the same `message` slot beneath the field, so nothing shifts as validation state changes:

```
┌─────────────────────────────┐
│ Password                    │
│ ┌─────────────────────────┐ │
│ │ ••••••              👁  │ │
│ └─────────────────────────┘ │
│ ✓ At least 8 characters     │   <- Constraint, live
│ ○ One number                │   <- Constraint, unmet
│ ⚠ Appeared in a breach      │   <- Issue, severity warning
└─────────────────────────────┘
```

The slot is `data-slot="field-message"`, and `state="invalid"` is set only when an `error`-severity issue is visible — so a warning colours the message without blocking submission or marking the field red.

## Events

22 distinct `on*` props today. They collapse to three, and each carries **why**, not just what.

```ts
onChange?:          (value: T, reason?: ChangeReason) => void;
onOpenChange?:      (open: boolean, reason?: OpenChangeReason) => void;
onSelectionChange?: (keys: K[], reason?: ChangeReason) => void;

type OpenChangeReason = "escape" | "backdrop" | "trigger" | "api" | "select" | "submit";
type ChangeReason     = "input" | "paste" | "clear" | "step" | "select" | "api";
```

The reason is optional and trailing, so `onOpenChange={(open) => …}` is unchanged.

**It exists because the library already drew this distinction.** `Drawer` ships `DrawerCloseReason = "escape" | "backdrop" | "trigger" | "api"`, and folding `onClose` into `onOpenChange(boolean)` would have thrown it away. Whether a dialog closed by Escape or by a backdrop click is exactly what decides whether to warn about unsaved work.

| Kept | Absorbs |
| --- | --- |
| `onChange` | `onInput` (12 sites), `onValueChange` (3), `onToggle` (3), `onSizeChange` (3) |
| `onOpenChange` | `onClose` (24), `onOpen` (3) |
| `onSelectionChange` | `onSelect` (3), `onDaySelect` (6) |

`onAction` (9) and `onInteractOutside` (9) stay distinct: activating an item is not changing a selection, and interacting outside is not necessarily closing.
